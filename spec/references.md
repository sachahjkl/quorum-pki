# Standards selection and provenance

Primary sources inspected on 2026-10-04. Links identify standards, not claims that this PoC conforms to every part of them. No protocol below supplies organizational independence or correct domain validation by itself.

| Source | Status / exact role | Implemented reuse or deliberate exclusion |
|---|---|---|
| [RFC 5280](https://www.rfc-editor.org/rfc/rfc5280.html) | PKIX certificate/path profile | Real DER roots and leaf certificates, SAN, SPKI, server-auth EKU, key usage and validity checked through Go `crypto/x509`. Local roots only; no public roots, OCSP, CRL distribution or full browser policy. |
| [RFC 8555](https://www.rfc-editor.org/rfc/rfc8555.html) | ACME automation and independent domain control challenges | Studied as an adapter for existing issuers, not implemented. The fixture owner signature is not an ACME challenge. A production system could obtain independent same-SPKI certificates through existing ACME servers. |
| [RFC 9162](https://www.rfc-editor.org/rfc/rfc9162.html) | CT v2, Experimental; obsoletes RFC 6962 as a specification | Exact §2.1 SHA-256 tree construction, inclusion and consistency algorithms. Custom Entry leaves, signed Head and API; no SCT, MMD, TransItem, registered log IDs or CT-v2 wire compatibility. |
| [RFC 6962](https://www.rfc-editor.org/rfc/rfc6962.html) | CT v1; historical/deployed ecosystem context | Studied, no SCT integration. RFC obsolescence alone does not imply browsers/logs all migrated to CT v2. |
| [JCS RFC 8785](https://www.rfc-editor.org/rfc/rfc8785.html) | Informational deterministic JSON serialization | Restricted ASCII/safe-integer subset giving the same canonical bytes. General IEEE-754 formatting and Unicode are deliberately excluded. |
| [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html), [RFC 7493](https://www.rfc-editor.org/rfc/rfc7493.html) | JSON and I-JSON interoperability | Reject duplicate object members and out-of-profile values; strict fixed objects. |
| [JSON Schema Draft 2020-12](https://json-schema.org/draft/2020-12) | Core and validation vocabularies | Strict schemas, local refs, offline fixture validation. Go uses typed decoding and semantic checks, not a general evaluator. JSON Schema cannot validate signatures, quorum intersections or history. |
| [JWS RFC 7515](https://www.rfc-editor.org/rfc/rfc7515.html), [RFC 8037](https://www.rfc-editor.org/rfc/rfc8037.html) | JOSE protected headers/signing input; Ed25519 | Detached signing-input construction, protected `alg/kid/typ`. Minimal EdDSA-only profile; no JWT, unprotected headers, compression, arbitrary alg negotiation or encryption. |
| [COSE RFC 9052](https://www.rfc-editor.org/rfc/rfc9052.html), [RFC 9053](https://www.rfc-editor.org/rfc/rfc9053.html) | Structured signatures over CBOR | Studied and excluded from the JSON-first implementation. COSE_Sign could represent independent signatures, but adding CBOR would create a second canonical encoding. |
| [Ed25519 RFC 8032](https://www.rfc-editor.org/rfc/rfc8032.html) | Recognized signing primitive | Standard-library implementation, no bespoke elliptic-curve code. |
| [FROST RFC 9591](https://www.rfc-editor.org/rfc/rfc9591.html) | IRTF Informational threshold Schnorr protocol; not an IETF Standards Track standard | Compared, not implemented. Threshold signature can compact finality to one signature, but adds nonce management, share lifecycle and two signing rounds. Distributed key generation is outside the main RFC scope; using FROST does not implement consensus or membership governance. |
| [DNSSEC RFC 4033](https://www.rfc-editor.org/rfc/rfc4033.html), [4034](https://www.rfc-editor.org/rfc/rfc4034.html), [4035](https://www.rfc-editor.org/rfc/rfc4035.html) | Hierarchical signed DNS delegation | Alternative trust path studied, not implemented. Does not establish independent CA quorum and retains DNS hierarchy trust. |
| [DANE RFC 6698](https://www.rfc-editor.org/rfc/rfc6698.html), [7671](https://www.rfc-editor.org/rfc/rfc7671.html) | TLSA binding of TLS service credentials via DNSSEC | Compared with the CA overlay. Different authority delegation, not a substitute for this quorum/finality policy. |
| [BCP 14 RFC 2119](https://www.rfc-editor.org/rfc/rfc2119.html), [8174](https://www.rfc-editor.org/rfc/rfc8174.html) | Normative keyword conventions | Used in experimental specification; this does not imply IETF endorsement. |
| [Transparency.dev system design](https://transparency.dev/how-to-design-a-verifiable-system/) | Transparency role/claim analysis | Adopt distinction between assertions, logs, monitors and independent comparison. The witness API here is custom and not compatible with external witness protocols. |
| [Practical Byzantine Fault Tolerance](https://pmg.csail.mit.edu/papers/osdi99.pdf) | Primary BFT algorithm paper | Used for architectural comparison. The code has durable notarization locks, not PBFT rounds, view changes or its liveness guarantees. |

Signed data need no Merkle-root field inside the entry; that would be circular. Current authorization needs a state commitment, not just CT-style historical inclusion. Independent signatures were selected because Go's standard library, operator accountability and easier certificate integration matter more to this PoC than aggregate-signature size.

No live root-store count is assumed. Root certificates, CA brands and independently governed operators are different counting units. Deployment threshold policy should be based on operator independence and usable issuer coverage, rather than a fixed number of roots allegedly present in every browser.
