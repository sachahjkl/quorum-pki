What this demonstrates

A certificate authority normally has the power to certify a domain’s public key on its own. This experiment adds a client-enforced rule: several independent operators must approve the same binding before it can be accepted.

  1. ProposeRequest a domain → public key binding.
  2. ApproveAuthorities check the request and sign independently.
  3. FinalizeA separate quorum signs the log and current-state roots.
  4. VerifyThe client checks signatures, proofs, freshness and its saved checkpoint.
Quorums, rotation and the trust assumptions

Approval is not finality. With the default five operators, three approvals authorize a binding. Four checkpoint signatures finalize its position and resulting state. These thresholds serve different purposes: two compromised operators cannot authorize a false binding, while overlapping finality quorums prevent conflicting decisions under the configured fault assumptions and durable honest voting locks.

Rotation preserves an overlap. A new key is published before activation. Advance the virtual clock to observe the scheduled state, the period where both keys are accepted, and retirement of the old key. Revocation disables the binding; recovery uses a separate preconfigured credential. A heartbeat refreshes the checkpoint without extending key validity.

The log records history; the state tree identifies the current binding. Merkle proofs let a client check both without downloading the whole registry. A saved checkpoint helps reject rollback. Witnesses can expose contradictory signed views when those views are compared.

This is a local sandbox. Domain ownership is represented by a signed fixture, not a live ACME challenge. The operators use real Ed25519 signatures and X.509 certificates, but share one demonstration environment. The finality protocol can stall after incompatible partial votes; leader changes and dynamic membership are not implemented. Its security depends on the pinned federation, independent operators, honest domain checks and durable checkpoints.

Start by issuing example.com. For a forgery test, set malicious operators, apply/reset, then propose a false key: one or two cannot reach approval quorum; three can. Reset creates a fresh simulation, not a recovery of the previous federation.

Scenario results

Each scenario runs real signatures and verification in an isolated simulation. A passing attack scenario means the outcome matches its assumptions; threshold compromise is expected to succeed.

Approval ≠ finality. Without enough reachable authorities, writes stop. Current-key acceptance requires a fresh checkpoint and an authenticated state proof.
